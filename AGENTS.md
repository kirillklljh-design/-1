# Руководство по работе с репозиторием

## Структура проекта и организация модулей

В рабочем каталоге пока нет исходного кода приложения, тестов, ресурсов и конфигурации сборки. При добавлении первого проекта создайте понятную структуру и обновите это руководство.

- Храните документацию и конфигурацию проекта в корне репозитория.
- Размещайте код приложения в `src/`, тесты в `tests/`, а статические ресурсы в `assets/`, если такая структура подходит выбранному фреймворку.
- Если каталог будет содержать несколько сайтов, выделите каждому отдельную папку с понятным названием и собственной инструкцией по настройке.
- Исключайте из системы контроля версий результаты сборки, каталоги зависимостей и локальные файлы редактора.

## Команды сборки, тестирования и разработки

Система сборки, менеджер пакетов и команды разработки пока не настроены. Не считайте команды вроде `npm test` или `npm run build` доступными без проверки.

При добавлении инструментов укажите в `README.md` проекта точные команды установки, локального запуска, сборки для публикации и тестирования. Добавьте в репозиторий соответствующий файл фиксации версий зависимостей и убедитесь, что описанные команды работают из указанного каталога.

## Стиль кода и правила именования

Соблюдайте соглашения выбранного языка и фреймворка. Используйте единообразные отступы внутри каждого файла и понятные имена переменных и функций. Для каталогов сайтов и статических ресурсов используйте строчные буквы и дефисы, например `landing-page/` и `hero-banner.svg`.

При появлении исходного кода добавьте общую конфигурацию форматирования и проверки стиля. Отделяйте изменения форматирования от несвязанных функциональных изменений.

## Правила тестирования

Фреймворк тестирования и минимальный порог покрытия пока не настроены. После выбора фреймворка добавляйте тесты вместе с новой функциональностью. Названия тестов должны описывать проверяемое поведение и ожидаемый результат. Документируйте запуск тестов и необходимую настройку окружения. При визуальных изменениях проверяйте интерфейс на актуальных размерах экрана и фиксируйте результаты ручной проверки, пока автоматические проверки отсутствуют.

## Коммиты и запросы на слияние

История Git отсутствует, поэтому существующие соглашения о коммитах определить нельзя. Используйте краткие заголовки в повелительной форме, например `Добавить макет главной страницы`. Посвящайте каждый коммит одной задаче.

В запросе на слияние объясняйте изменения, добавляйте ссылки на связанные задачи и описывайте выполненные проверки. При изменениях интерфейса прикладывайте скриншоты. Указывайте изменения конфигурации и зависимостей.

## Безопасность и конфигурация

Не добавляйте в репозиторий учётные данные, ключи API и локальные файлы окружения. Если нужны переменные окружения, предоставьте пример конфигурации с заглушками и опишите назначение переменных без раскрытия секретных значений.
